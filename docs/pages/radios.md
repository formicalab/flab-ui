# Wi-Fi radios (route `#radios`)

The radios as hardware, with everything that runs on them, to read and to change: a card per radio, refreshed every 5 s. A radio card holds the radio's live state and channel, its **wireless networks** (access points, client networks and 802.11s mesh points, each with what it is doing now and its settings) and its own **radio settings**. These are the objects of `/etc/config/wireless` (`wifi-device` and `wifi-iface`) that the [Devices and Interfaces](interfaces.md) board shows as a radio card holding its interfaces; a chip of the board opens this page. `#wifi` and `#mesh` open this page. The connected clients are on the [Connected devices](connected.md) tab of Devices and Interfaces. Like the [Ethernet ports](network.md) page, this page shows each device's live state and keeps every configured value in one fold, so nothing is shown twice. The page is `radios/index.js`, the cards `radios/card.js`, the networks of a card `radios/networks.js`, the mesh live part `radios/mesh.js`, the display parts `radios/parts.js`; the editing (the schema, the model, the controls, the channel picker) is in `wifi/` (`schema.js`, `model.js`, `editors.js`, `channels.js`, `picker.js`, the draft and the review banner in `editor.js`).

**Reading**: `flab.radio status` gives the radios, `flab.radio config` the wireless configuration, `flab.mesh status` the peers, paths and parameters of the mesh points (the wired `flab.network status` is only read for the spanning-tree role of a mesh port). Summary tiles hold the totals no card shows (radios up, clients, mesh peers when there is a mesh point, the busiest channel), then a card per radio: the header (state dot, name, band, phy, state, supported standards, and the hardware: the wireless chip, the kernel driver, the bus and the PCI or USB id, detected from `iwinfo` and sysfs; the hardware modes and the device-tree compatible string are its tooltip), the key figures (running channel and frequency, width and center, TX power in dBm and mW with the regulatory limit of that channel, noise floor, antenna chains; the channel, width and power each carry the configured value in their sub line, so what runs and what is asked for are side by side), the findings when something is off (radio down, setup failing, a running channel different from the configured one, high noise, a busy channel, a DFS availability check in progress, an open network, a country that differs from the regulatory domain, and the findings of its mesh points), the channel utilization (busy, RX and TX airtime as a percentage and a chart, derived in the browser from the driver's cumulative survey counters) on its own; the channels are an option like the others and are chosen in the radio settings (the picker, below), where a login that may not write sees a plain strip with the running block highlighted and the DFS (radar) channels marked. A router that cannot report the configuration shows that strip in the card. The other configured options (country, cell density, beacon interval, options, the device path) are only in the radio settings. `status` copies only whitelisted options: keys, passwords, FT key material and MAC lists never leave the router through it.

**Wireless networks** (`radios/networks.js`, the editor in `wifi/editors.js`): one foldable block per `wifi-iface` of the radio, with the buttons **Add access point**, **Add client network** and **Add mesh point**. The summary line says what the block is (the SSID or Mesh ID, access point, client or mesh, the encryption, running or not) and how it is doing (the clients of an access point, a BSS state such as the DFS availability check, the peers and the weakest link of a mesh point). The body shows what the interface is doing now, above the settings: for an access point or a client network its interface, BSSID, the traffic now and the totals; for a mesh point the peers, paths and parameters (below). What is configured is shown once, in the settings, so the live part has no feature chips or repeated options. A router whose plugin cannot report the configuration gets the same blocks without settings. Every fold of the page (the network blocks, the groups and the Settings fold, the folded mesh paths and parameters) is built with `disclosure()` of `core/fold.js`, so they all share one arrow. **WPS**: an access point that has the WPS push button enabled (`wps_pushbutton`, WPA2-Personal) shows a **WPS** button in its summary line (`radios/wps.js`). After a confirmation that says that any device in range pressing its WPS button joins without the password, it calls `flab.radio wps` (`action` `start`), which asks hostapd (`hostapd.<if> wps_start`) to accept the button for two minutes; while it is open the line shows the time left and the button cancels it (`wps_cancel`). The method refuses an interface that is not a running access point with the option set, and is the only write method of the plugin outside `uci`, so a login that may not write sees no button.
- **Access points and client networks** (`mode ap` and `sta`): the options of the OpenWrt wireless documentation in groups: network (SSID, the networks it is attached to, a check box per network interface of the router, encryption, password, hidden, disable, the BSSID of a client), enterprise authentication, security options, clients and traffic, roaming 802.11r/k/v. Encryption offers what the installed hostapd can do (SAE, OWE and WPA-Enterprise only when `hostapd -vsae`, `-vowe`, `-veap` succeed; a value the file already holds, such as WEP or TKIP, stays selectable). An option that does not apply to the mode or the encryption is hidden, keeps its value in the file and is not written. A new network is added as a named section (`wifinetN`); a section without a name (`cfgXXXXXX`) is addressed by its generated name, and the check after a save finds the networks by position because that name changes with the content.
- **Mesh points** (`mode mesh`, the [OpenWrt 802.11s page](https://openwrt.org/docs/guide-user/network/wifi/mesh/802-11s)): the wireless configuration of a mesh point is its **Mesh ID** (`mesh_id`, 1 to 32 bytes), the networks it is bridged into, the encryption (SAE or open; encrypted needs a wpad with mesh support, `wpad-mesh-*` or the full wpad, and a router whose wpad lacks SAE gets an error that says so), the password and, among the mesh options, the multicast rate (`mcast_rate`, kb/s). Every node of the mesh must use the same Mesh ID, channel and password. The **mesh parameters** (forwarding, RSSI threshold, HWMP root mode, gate announcements and the rest) can only be set once the interface is up, so `/etc/config/wireless` cannot hold them: they are shown read only as the values in force (`iw get mesh_param`), with the note that they are set with `iw` from a hotplug script or with the `mesh11sd` package. The live part shows the spanning-tree role of the mesh port in its bridge, the peers (link state, signal and average, TX and RX bit rate, expected throughput, airtime metric, retries and failed transmissions, the live traffic, idle and connected time, the gate flag), the folded mesh paths (destination, next hop, hops, metric, expiry and the decoded flags) and the folded parameters. The findings are no peer, a peer not established, a weak link (-75 dBm or less), more than 10 % failed transmissions, forwarding off and unresolved paths. Warnings when a mesh point is added or changed: **spanning tree does not see a mesh** (frames enter the mesh after the bridge's spanning tree), so a cable between mesh nodes in the same bridge loops, and so do two mesh points on one network; changing the Mesh ID, the password, the encryption or the networks, or removing the mesh point, disconnects its established peers; an open mesh lets any device with the Mesh ID and channel in. The mesh key is never read: only whether one is stored.

**Radio settings**: a foldable block under the key figures of each card, above the wireless networks (its summary line shows the configured mode, country and power) with the options of a `wifi-device` section of the [OpenWrt wireless documentation](https://openwrt.org/docs/guide-user/network/wifi/basic), each with a hint taken from it, in three groups:
- **Radio**: disable the radio, mode and channel width (`htmode`), the channels automatic selection may use (`channels`, a list of channels and ranges, shown while the channel is automatic), country, transmit power (`txpower`).
- **Rates and coexistence**: cell density, legacy 802.11b rates, minimum client standard (`require_mode`), the coexistence scan (`noscan`) and the HT coexistence flag (`ht_coex`) on 2.4 GHz, beacon interval, the basic and supported rates (`basic_rate`, `supported_rates`, lists in kb/s that override the cell density).
- **Advanced**: the country advertisement (`country_ie`, 802.11d), distance, RTS and fragmentation thresholds, antenna gain, the hostapd log level, automatic antenna selection and the receiving and transmitting antenna (`diversity`, `rxantenna`, `txantenna`, used by some drivers only), the narrow channel width (`chanbw`, 5, 10 or 20 MHz; ath9k and ath5k only, so it is shown only where the file already sets it), the high throughput capabilities (`ht_capab`, detected by themselves) and extra hostapd options (`hostapd_options`, passed as they are).
The block also says how the radio is identified in the file (`type`, `phy`, `radio`, `macaddr`, `path`, `band`: detected by themselves, not edited here). The mode list is what the hardware reports: the htmodes `iwinfo` lists for a running interface, else the widths the phy's capabilities advertise for the radio's band (HT, VHT, HE, EHT; the explicit `HT40+` and `HT40-` on 2.4 GHz and `NOHT` are added); a radio whose phy is unknown gets a text box checked for its form. The country list comes from the driver (`iwinfo <if> countrylist`), else a text box. Options that apply to one band are shown on it (legacy rates, the coexistence scan and the HT coexistence flag on 2.4 GHz) or when they are already set. The lists are validated one entry at a time (a channel or a range such as `36-48`, a rate in kb/s, a capability such as `SHORT-GI-40`).

**The channel picker** (`wifi/channels.js` model, `wifi/picker.js` control): the **Radio** group of the radio settings (open, under the mode and the other radio options, since the mode decides which channels fit) shows the radio's allowed channels as tiles, with the regulatory domain named under them. The
`channel` option of the radio is a channel number or `auto`; a channel is only selectable when the whole block of the width of the mode
being edited fits around it in the regulatory domain (others are hatched), so choosing a mode redraws which blocks fit, and a mode that
no longer fits the chosen channel is an error on both controls.
- **Preview**: hovering or focusing a tile shows the block the radio would use at that width, in blue,
  or in red with the reason when it does not fit. The block is made of whole 20 MHz channels: on 5 and 6 GHz the
  fixed blocks (36-48 at 80 MHz, 100-128 at 160 MHz); on 2.4 GHz a 40 MHz block is the channel and the one four
  numbers away, on the side netifd picks (channels 1-6 above, 7-13 below, or an explicit `HT40+`/`HT40-`), so
  channel 4 with channel 8 covers 2417-2457 MHz. The channels between the two are shown as covered, the ones that
  stick out as partly overlapped (dashed). The sentence under the tiles says the same in words.
- **Choosing**: a click selects (green, with its block tinted), a second click undoes it; the Auto chip hands the
  choice to the radio. The yellow review banner lists the change from and to, with warnings that do not block Save:
  a block that reaches radar (DFS) channels (the radio listens for radar for 1 to 10 minutes before clients can
  connect), `auto`, and a radio that carries a mesh interface (the other mesh nodes must be moved to the same
  channel by hand). A channel the regulatory domain disables, or whose block does not fit, is an error that
  blocks Save.

**Validation and saving**: only what the draft changes is checked, so an odd configuration does not block an unrelated edit. Secrets are never read (the configuration is read through `flab.radio config`, which reports only that a `key`, `sae_password`, RADIUS secret, EAP identity or password, private-key password, WPS PIN or key-holder list is set, and never through `uci get`); password fields are write-only: they are empty and say "stored; leave empty to keep it", a typed value replaces the stored one and is never shown in the review list. Errors block Save and mark the control; warnings do not. The change is staged, applied with the rollback countdown (rpcd reloads Wi-Fi), read back through `flab.radio config` and compared option by option (a typed password: that one is now stored), and each changed radio must be up with its new or changed networks running within 16 seconds (a radio that is switched off, or has no enabled network, is not waited for; a radio on a DFS channel counts as up while it listens for radar); if the check or the wait fails the change is rolled back.
- **Radio errors**: a mode the hardware does not report, a country the driver does not know, a channel the new mode cannot carry, numbers out of range, a malformed channel, rate or capability. **Radio warnings**: switching a radio off (how many networks and clients it takes down, and that the router undoes the change by itself 30 seconds after the apply if the admin loses the connection), changing the country, a power above the regulatory limit of the channel, a 40 MHz channel on 2.4 GHz, legacy rates, requiring 802.11ac, a block that reaches radar channels.
- **Network errors**: an SSID or Mesh ID over 32 bytes or empty, a network attached to nothing, a password that is not 8 to 63 printable ASCII characters or 64 hexadecimal digits, a missing password on a protected network (a stored one counts), an encryption the hostapd cannot do, missing RADIUS or EAP fields, protected management frames disabled with WPA3 or OWE, malformed MAC addresses or 802.11r identifiers, numbers out of range. **Network warnings**: changing the SSID, password, encryption, networks, protected frames or hiding of a network that has clients (their number, and that the admin may be connected through it), removing or disabling a running network, an open network (who can join and what they reach), WEP, WPA1 or TKIP, two networks with the same SSID on one radio, an access point and a client network sharing a radio (they share its channel), an allow filter with an empty list, 802.11r settings that break fast transition with WPA3, a hidden SSID, and the mesh warnings above.
- Polling is suspended while edits are pending, a control has the focus, the pointer is over the channel picker or a save runs. A login that may not write gets the controls read only with a note; a router whose `flab.radio` has no `config` method gets the radios and networks read only with a note and the plain channel strip.
- The page needs the ACL fragment `rpcd/acl.d/flab-radio.json` (`flab.radio` `status` and `config`, `uci changes` and the `uci` write methods on `wireless`, no `uci get`); the mesh points use `flab.mesh status` (`flab-mesh.json`) and the spanning-tree role `flab.network status` (`flab-network.json`), both optional.
